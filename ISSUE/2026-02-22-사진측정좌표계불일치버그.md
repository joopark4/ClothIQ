# 사진 측정 앵커 좌표계 불일치 버그 (가로/세로 레이아웃)

**날짜**: 2026년 02월 22일
**상태**: ✅ 해결 완료
**심각도**: High
**영향 범위**: PhotoMeasurementView, ZoomableImageView, MeasurementLinesOverlay, PhotoMeasurementViewModel

---

## 문제 현상

### 증상
- 사진 측정 화면에서 탭하여 앵커를 배치하면, 앵커가 탭한 위치와 다른 곳에 표시됨
- 이미지 회전(가로/세로 전환) 시 앵커 위치 오차가 더욱 두드러짐
- 의류 라이브러리에서 기존 측정값의 라인 오버레이가 잘못된 위치에 표시됨

---

## 발견된 버그 3가지

### 버그 1: Y축 반전 불일치 (저장 ↔ 로드)

**파일**: `PhotoMeasurementViewModel.swift:427-434`

```swift
// ❌ 저장 시 (normalizeFinalImagePoint, L535): Y 반전 없이 SwiftUI 좌표 그대로 저장
y: clamp(point.y / size.height, ...)  // 반전 없음

// ❌ 로드 시 (loadAnchors, L429): Vision 좌표계로 가정하고 (1.0 - y) 반전 적용
y: (1.0 - start.y) * imageSize.height  // ← 잘못된 반전
```

**결과**: 탭한 y=300 → 저장 0.3 → 로드 시 (1-0.3)\*height = 0.7\*height. 앵커가 항상 Y 반전된 위치에 표시됨.

---

### 버그 2: rotation이 좌표 변환에 미반영

**파일**: `ZoomableImageView.swift`

- `convertTapLocation` (L146): `image.size`를 기반으로 aspect ratio 계산, `rotation` 무시
- `convertImageToViewCoordinates` (L390): `imageSize`를 기반으로 계산, `rotation` 무시
- `convertViewToImageCoordinates` (L431): `imageSize`를 기반으로 계산, `rotation` 무시

```swift
// ❌ rotation 무시한 계산
let imageAspect = image.size.width / image.size.height  // rotation 무시
```

90°/270° 회전 시 화면에 표시되는 이미지의 실질적 width/height가 교환되는데, 좌표 변환에선 여전히 원본 비율 사용 → 앵커가 완전히 다른 위치에 표시됨.

---

### 버그 3: `MeasurementLinesOverlay`의 Y축 반전

**파일**: `MeasurementLinesOverlay.swift:210-217`

```swift
// ❌ 저장된 좌표를 Vision 좌표계로 가정하고 (1.0 - y) 적용
let start = CGPoint(
    x: displayRect.minX + startPoint.x * displayRect.width,
    y: displayRect.minY + (1.0 - startPoint.y) * displayRect.height  // 잘못된 Y flip
)
```

## 근본 원인

**좌표계 혼동**: 저장 시에는 SwiftUI 좌표계(top-left origin, Y증가=아래방향)로 저장하는데, 로드/표시 시에는 Vision 좌표계(bottom-left origin, Y증가=위방향)로 가정하고 `(1.0 - y)` 변환을 적용함.

**rotation 미반영**: `rotationEffect(.degrees(rotation))`은 SwiftUI의 시각적 회전만 수행하고 내부 좌표는 그대로임. 따라서 90°/270° 회전 시 표시 이미지의 가로세로 비율이 바뀌는데, 좌표 변환 함수들이 이를 반영하지 않음.

**파일**: `ZoomableImageView.swift:146`

```swift
// After ✅ - rotation 반영한 aspect ratio 계산 + 역변환

let displayedHeight = isRotated90or270 ? imageSize.width : imageSize.height

// ...

switch normalizedRotation {
case 90:
    imageX = imageSize.width * (1 - relativeY)
    imageY = imageSize.height * relativeX
case 180:
    imageX = imageSize.width * (1 - relativeX)
    imageY = imageSize.height * (1 - relativeY)
case 270:
    imageX = imageSize.width * relativeY
    imageY = imageSize.height * (1 - relativeX)
default:
    imageX = imageSize.width * relativeX
    imageY = imageSize.height * relativeY
}
```

### 버그 4: 역방향 변환 함수에서 90°/270° 케이스 코드 뒤바뀜

**파일**: `ZoomableImageView.swift`
**영향 함수**: `convertTapLocation`, `convertViewToImageCoordinates`

수학적 검증 결과, 정방향 함수 `convertImageToViewCoordinates`는 올바르지만,
역방향 함수(`convertTapLocation`, `convertViewToImageCoordinates`)의 90°/270° 케이스가 서로 뒤바뀌어 있었음.

**정방향 (이미지→뷰)**:
- 90°: `dx = 1-ny, dy = nx`
- 270°: `dx = ny, dy = 1-nx`

**역방향 공식 (뷰→이미지)**:
- 90°: `nx = dy, ny = 1-dx` (뒤바뀐 코드: `nx = 1-dy, ny = dx` — 실제로는 270° 공식)
- 270°: `nx = 1-dy, ny = dx` (뒤바뀐 코드: `nx = dy, ny = 1-dx` — 실제로는 90° 공식)

**결과**: 90° 및 270° 회전 상태에서 탭/드래그 위치가 반대쪽으로 잘못 계산됨.

### 버그 5: convertTapLocation에서 imagePadding 미반영

**파일**: `ZoomableImageView.swift`

`MeasurementAnchorsOverlay`는 `padding = imagePadding(20)`을 적용하여 이미지 표시 크기를 계산하지만,
`convertTapLocation`은 `viewSize` 전체를 사용 → 두 함수의 표시 크기 계산이 불일치.

**파일**: `ZoomableImageView.swift`

좌표 변환 로직을 단일 `CoordinateConverter` 구조체로 추출.

- `convertTapLocation`, `convertImageToViewCoordinates`, `convertViewToImageCoordinates` 모두 `CoordinateConverter` 위임으로 교체
- `convertTapLocation`이 `padding: imagePadding` 사용 → 표시 크기 계산 일치

```swift
// CoordinateConverter 정방향 (imageToView):
// 0°:   dx = nx,   dy = ny
// 90°:  dx = 1-ny, dy = nx
// 180°: dx = 1-nx, dy = 1-ny
// 270°: dx = ny,   dy = 1-nx

// CoordinateConverter 역방향 (viewToImage, 수정됨):
// 0°:   nx = dx,   ny = dy
// 90°:  nx = dy,   ny = 1-dx   ← 수정 (기존: nx=1-dy, ny=dx)
// 180°: nx = 1-dx, ny = 1-dy
// 270°: nx = 1-dy, ny = dx     ← 수정 (기존: nx=dy, ny=1-dx)
```

## 교훈

### 좌표계 일관성 원칙

**핵심**: 저장과 로드, 표시에 사용하는 좌표계를 반드시 일치시켜야 함.

- **SwiftUI**: top-left origin, Y 증가 = 아래방향
- **Vision Framework**: bottom-left origin, Y 증가 = 위방향 (ARKit 정규화 좌표와 동일)
- **저장 시 결정**: `normalizeFinalImagePoint`에서 어떤 좌표계로 저장하는지 명확히 문서화
- **로드/표시 시 일치**: 저장한 좌표계와 동일하게 처리

### rotationEffect vs 좌표 변환

**핵심**: `rotationEffect(.degrees(n))`은 **시각적 회전만** 수행.

- 내부 좌표계는 그대로 유지됨
- 90°/270° 회전 시 표시 이미지의 가로세로 비율이 사실상 바뀜
- 좌표 변환 함수는 rotation 값을 직접 반영하여 aspect ratio와 좌표 역변환을 처리해야 함

### 정방향-역방향 수학 검증 원칙

**핵심**: 좌표 변환 쌍(정방향/역방향)은 반드시 수학적 역함수 관계를 검증해야 함.

정방향 f(p) = q 라면, 역방향 g(q) = p 를 코너 포인트(TL/TR/BR/BL)로 직접 계산하여 검증.

```
90° CW 예시 (imageSize = W×H):
  정방향: 이미지 (0,0)TL → dx=1-0=1, dy=0 → 뷰 오른쪽 위
  역방향: dx=1, dy=0 → nx=dy=0, ny=1-dx=0 → 이미지 (0,0) ✅
```

### 단일 변환기 패턴 (CoordinateConverter)

중복된 좌표 변환 로직이 여러 함수에 분산되면:
- 한 곳의 버그가 부분적으로만 수정되어 불일치 발생
- 새 케이스(새 회전 각도 등) 추가 시 모든 함수를 수정해야 함

→ 단일 `CoordinateConverter` 구조체로 캡슐화하면 이 문제 해결.
